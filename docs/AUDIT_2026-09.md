# USMA Audit — September 2026

**Scope:** full review of the implementation (correctness, performance, architecture),
the signal-processing and statistical method, and every Markdown document in the
repository including agent/context instructions.
**Version audited:** v0.12.4 (`APP_VERSION = "0.12.4"`, branch `master`).
**Companion documents:** `THEORY.md` (canonical maths), `docs/SPEC_CLASSIFICATION_V2.md`
(approved redesign), `CHANGELOG.md`, `AGENTS.md`.

---

## 0. Method and its limits

Every finding below was established by one of three means, stated per finding:

1. **Execution against real data.** The `_calibration` blocks stored in
   `configs/*.json` contain 60 expert-labelled signals across three sessions.
   `HybridCalibrationEngine` was reconstructed from them with `from_dict()` and
   run. This is the primary evidence and it is reproducible (Appendix A.2).
2. **Numerical demonstration.** Where a mechanism needed isolating, it was
   reproduced on synthetic traces with the project's own filter and FFT settings
   (Appendix A.1). Synthetic results are used only to explain a mechanism, never
   as evidence of field behaviour.
3. **Static reading.** Used only for structural claims (dead code, imports,
   documentation contradictions) where execution adds nothing.

**Statistical limitation, stated up front.** The labelled sets are small: 24, 19
and 17 signals, with GOOD/BAD splits of 20/4, 13/6 and 9/8. A ROC AUC computed on
9 versus 8 samples has a 95 % confidence interval roughly 0.30 wide. Consequently
**this audit can demonstrate the absence of evidence for separation; it cannot
prove that separation is absent.** Where a measured AUC is quoted, the conclusion
drawn is always "no separation has been demonstrated", never "the metric is
proven useless". Section S-1 depends on this distinction and so does any use of
these numbers in a publication.

**Severity scale.** **Blocker** — produces a crash or a wrong scientific result in
normal operation. **Major** — undermines a claim the project makes about itself.
**Minor** — correctness, clarity or efficiency, no scientific consequence.

## 2. Correctness (C)

### C-1 — NumPy 2.0 removed `np.trapz`; the shipped runtime cannot run the ROC estimator  · **Blocker · verified by execution**

`usma/models.py` called `np.trapz` at two sites (`ROCYoudenEstimator._youden_threshold`
and `HybridCalibrationEngine.get_roc_data`). `np.trapz` was **removed** in NumPy 2.0
and replaced by `np.trapezoid`. The bundled portable runtime is
`numpy-2.2.6-cp311-cp311-win_amd64` (`python/Lib/site-packages/`).

Reconstructing the engine from the real `PSD_FRF_ONLY_SMNS.json` session
(9 GOOD / 8 BAD) and calling it:

```
reconstructed: good=9 bad=8 level=4
roc.can_estimate = True
get_estimates()         -> AttributeError: module 'numpy' has no attribute 'trapz'
get_estimates_by_type() -> AttributeError: module 'numpy' has no attribute 'trapz'
roc.estimate()          -> AttributeError: module 'numpy' has no attribute 'trapz'
get_roc_data()          -> AttributeError: module 'numpy' has no attribute 'trapz'
```

`ROCYoudenEstimator` becomes eligible only at ≥ 5 GOOD **and** ≥ 5 BAD, so the
failure is confined to — and total within — exactly the Level 3/4 regime that
`README.md` and `THEORY.md` §5.4–5.5 present as the high-confidence path.

Three consequences matter beyond the crash:

- **`ROCYoudenEstimator` has never executed in the shipped environment.** Any
  statement, in a paper or elsewhere, that USMA's calibration cross-validates three
  estimators describes code that has not run. The two stored sessions that reached
  "Level 4" did so with fewer than 5 BAD signals, so ROC was skipped and no error
  surfaced — which is why this went unnoticed.
- **The ROC subplot in Cal. Diagnostics has never rendered** for a balanced session.
- **`usma/analysis/coherence.py` used `np.trapezoid`**, which does *not* exist before
  NumPy 2.0. There was therefore **no NumPy version on which both code paths worked**:
  1.x broke coherence analysis (silently — the call sits inside a broad `except` that
  returns `None`), 2.x broke calibration.

**Fix.** A single `trapezoid()` helper in `usma/models.py` resolves the name once at
import; both modules use it. `requirements.txt` now pins `numpy>=1.22,<3` with the
reason recorded inline (D-3).

**Post-fix, same fixture:**

```
get_estimates(): fft_cutoff_frequency=0.02500, fft_energy_ratio_threshold=0.00954,
                 lowpass_cutoff=0.05000, relative_residual_ratio=0.02500,
                 exceedance_ratio_threshold=0.63215
[roc] fft_energy_ratio_threshold=0.00858  J=0.306  AUC=0.611
      exceedance_ratio_threshold=0.12411  J=0.111  AUC=0.368
      relative_residual_ratio=0.02        J=0.375  AUC=0.458
get_roc_data() -> ['fft_energy_ratio', 'exceedance_ratio', 'relative_residual_ratio']
```

Those AUC values are the engine's own verdict on its discriminants, and they are
finding S-1.

### C-2 — The calibration lowpass sweep filtered the residual, not the signal · **Blocker · verified by execution**

`PercentileBoundaryEstimator._sweep_filter_params` chose `lowpass_cutoff` by
re-filtering, per candidate cutoff, the array under the key `signal_vector`:

```python
signal = sig.get('signal_vector', sig.get('signal_physical'))
```

`MonitorControlGUI._build_calibration_signal_data` populated that key as:

```python
'signal_vector': sig.residual_physical,
```

— the **residual**. Confirmed against the stored data: for every session,
`signal_vector` is element-wise identical to `residual_physical` (`np.allclose →
True`, lengths 623 and 838). The sweep was therefore lowpass-filtering an
already high-passed array and optimising the cutoff against the residual *of the
residual*. Every `lowpass_cutoff` value ever produced by calibration is invalid.

**Fix.** `LightweightHitData` gains a `signal_pixels` field, populated from
`FRFAnalysisResult.signal_vector` (the pixel-space signal) at both the FRF and PSD
hit-record sites in `usma/monitor.py`. The GUI now passes `signal_pixels`; the key
`signal_vector` is no longer written. The sweep reads `signal_pixels` and falls
back to `signal_physical`.

**On the fallback:** `signal_physical` is an affine image of the pixel signal, and
the exceedance ratio is invariant under affine rescaling (the threshold is
`ratio × max|residual|`, so the scale cancels). The fallback is therefore *exact*,
not approximate, and legacy stored sessions replay correctly. Effect on the real
fixture: `lowpass_cutoff` moved from 0.07 to 0.05 (SMNS) and 0.19 → 0.03 (untyped
`PSD_FRF_ONLY`).

### C-3 — The same sweep ignored the configured filter order and ratio · Major · static

The sweep hardcoded `butter(7, …)` and a test ratio of `0.10`, so the cutoff was
optimised under a filter configuration the runtime need not be using — a user
running order 3 received a cutoff fitted at order 7. It also performed a
`from scipy.signal import sosfiltfilt` **inside the inner loop**, i.e. up to
17 × n times per estimate.

**Fix.** The import moved to module level. Each stored signal now carries its own
`relative_residual_ratio` and `lowpass_filter_order`, and the sweep uses them.

### C-4 — The Bayesian estimator for `relative_residual_ratio` was fed a constant · **Blocker · verified by execution**

`BayesianThresholdEstimator.update()` read its third observation as
`signal_data.get('relative_residual_ratio')`. The GUI supplied:

```python
'relative_residual_ratio': self.monitor.app_config.relative_residual_ratio  # or psd_
```

— the **current configuration value**, identical for every signal and identical for
GOOD and BAD. A Bayesian update requires a per-signal *observed* metric; for this
parameter none exists. The likelihood therefore alternated between
`sigmoid(s·(grid − c))` for each GOOD and `sigmoid(s·(c − grid))` for each BAD at
the same constant `c`, so the posterior depended only on how many of each had been
seen. Reproducing the exact grid and steepness from the source, with `c = 0.10`:

| GOOD | BAD | MAP |
|---|---|---|
| 3 | 3 | 0.1003 |
| 4 | 3 | 0.1067 |
| 3 | 4 | 0.0938 |
| 6 | 3 | 0.1163 |
| 3 | 6 | 0.0826 |
| 8 | 8 | 0.1003 |
| 10 | 6 | 0.1115 |

With balanced counts the estimator returns the value it was handed. With imbalance
it drifts in proportion to the imbalance. **No signal ever influenced it**, and the
95 % credible interval reported for it — described in `THEORY.md` §5.3 as "USMA's
principled measure of how sure we are about this threshold" — measured nothing.
At Level 2 this fabricated estimate carried 60 % of the merge weight
(`_merge_two(bayes_weight=0.6)`).

**Fix.** `relative_residual_ratio` removed from `PARAM_GRIDS` and `metric_map`, with
the reasoning recorded at the code site and in `THEORY.md` §5.3. It is now estimated
by the percentile and ROC sweeps only — both of which recompute the exceedance ratio
from each signal's own residual for every candidate ratio, which is a genuine
observation. Diagnostics consumers guard with `in` / `.get`, so the CI band simply
stops being drawn for that subplot, which is the honest rendering.

### C-5 — A swallowed filter exception produced a silent GOOD verdict · **Blocker · verified numerically**

`SignalAnalyzer.analyze` guarded the filter with `if len(pixel_detrended) < 15`, then
wrapped the call in `except Exception: filtered_detrended = pixel_detrended.copy()`.
`sosfiltfilt` requires `len(signal) > 3·(2·n_sections + 1) − 1`, which depends on
filter order:

| order | sections | required length | 15 | 20 | 30 | 50 |
|---|---|---|---|---|---|---|
| 3 | 2 | > 14 | ok | ok | ok | ok |
| 5 | 3 | > 20 | **fail** | ok | ok | ok |
| 7 *(default)* | 4 | > 26 | **fail** | **fail** | ok | ok |
| 10 | 5 | > 32 | **fail** | **fail** | **fail** | ok |

At the default order 7, any ROI 15–26 px wide passed the guard, raised inside
`sosfiltfilt`, was caught, and fell through to `filtered = detrended`. Then
`residual = detrended − filtered ≡ 0` → `max_abs_residual = 0` →
`dynamic_threshold = 0` → `exceedance_ratio = 0` → `lowpass_is_bad = False`.
**A filter failure was indistinguishable from a perfectly clean signal**, with no
warning logged. This is the failure mode that matters most: it converts an error
into a passing measurement verdict.

**Fix.** `_lowpass_detrended()` replaces the guard. It reduces the Butterworth order
until the signal is long enough (order 1 needs only 9 samples), logs the reduction at
INFO, and if no order fits logs a WARNING and returns `None`. `FRFAnalysisResult`
gains `lowpass_valid: bool`, set `False` in that case, so "LP says clean" is
distinguishable from "LP could not evaluate". The dead
`SignalAnalyzer._apply_lowpass_filter()` — never called, and reading
`self.app_config` rather than the per-family `params`, so it would have applied FRF
settings to PSD ROIs had it ever been wired up — was removed in the same change.

**Recommendation not taken:** `HitClassifier` still treats `lowpass_valid=False` as
"no BAD vote". Making the LP method *abstain* is the correct behaviour, but
abstention is exactly what `SPEC_CLASSIFICATION_V2.md` §5 introduces, so it belongs
with that work rather than as a local patch.

## 3. Method and signal processing (S)

### S-1 — Neither discriminant separates GOOD from BAD on USMA's own labelled data · **Major · verified by execution**

Every stored `_calibration` signal was scored against its expert label. The statistic
is `AUC = P(metric_BAD > metric_GOOD)`, computed with mid-ranks for ties; 0.5 means
no information, below 0.5 means the metric is ordered the wrong way round.

| Dataset | Family | GOOD / BAD | `energy_ratio` | `exceedance_ratio` | `max_abs_residual` |
|---|---|---|---|---|---|
| `PSD_FRF_ONLY` | FRF | 8 / 4 | 0.625 | 0.656 | 0.688 |
| `PSD_FRF_ONLY_SMNS` | PSD | 9 / 8 | 0.611 | **0.368** | 0.569 |
| `PSD_FRF_ONLY` | PSD | 12 / 0 | — | — | — |
| `no_OCR` | PSD | 0 / 1 | — | — | — |

The engine's own ROC estimator, once C-1 was fixed, independently reports
AUC = 0.611 / 0.368 / 0.458 on the balanced set — agreeing with the table.

**Reading this honestly.** At 9 versus 8 samples, none of these values is
distinguishable from 0.5; the inversion at 0.368 is equally not distinguishable from
0.5. The defensible statement is therefore: **across every labelled session USMA has
recorded, no discriminative power has been demonstrated for either method, in either
direction.** It is *not* established that the metrics are useless — the datasets are
too small for that. Two of the four family splits have one empty class and cannot
contribute at all.

This is the same conclusion `docs/SPEC_CLASSIFICATION_V2.md` §1 reaches from field
experience ("Field experience shows this cannot separate good from bad hits even
after calibration"), arrived at independently and from the data. The audit therefore
**supports the spec's premise** rather than contradicting it, and supplies part of
the evidence its §7.1 validation plan calls for.

**What would settle it.** The spec's §7 retrospective, run properly: per-method
confusion matrices on all stored sessions, with at least ~30 signals per family and
a GOOD/BAD split no worse than 2:1. The current sets are far from that, and
`PSD_FRF_ONLY` has 12 PSD GOOD and 0 PSD BAD — a labelling campaign, not an
algorithm change, is the prerequisite.

### S-2 — The shipped defaults are mis-scaled in opposite directions · **Major · verified by execution**

| Dataset | n | `energy_ratio` median (range) | fires at default 0.006 | `exceedance_ratio` median (range) | fires at default 0.70 |
|---|---|---|---|---|---|
| `PSD_FRF_ONLY` | 24 | 0.0896 (0.042–0.265) | **24 / 24** | 0.5419 (0.201–0.899) | 6 / 24 |
| `no_OCR` | 19 | 0.1159 (0.007–0.364) | **19 / 19** | 0.0000 (all zero) | 0 / 19 |
| `PSD_FRF_ONLY_SMNS` | 17 | 0.0092 (0.002–0.027) | 11 / 17 | 0.5501 (0.124–0.782) | 1 / 17 |

`fft_energy_ratio_threshold = 0.006` sits one to two orders of magnitude below the
observed values, so the FFT method votes BAD on essentially every hit.
`exceedance_ratio_threshold = 0.70` sits above nearly the whole observed range, so
the LP method almost never votes. Under the §4 rule a single BAD vote demotes a hit
to SUSPECT, so **out of the box USMA reports near-universal SUSPECT** — which is
consistent with the field experience recorded in the spec.

**Deliberately not changed, and why.** `energy_ratio` depends on ROI width, on the
plotted frequency span, and on how much of the ROI the trace occupies; the three
datasets differ from each other by an order of magnitude. No single global constant
is defensible, and picking one tuned on `PSD_FRF_ONLY` would make it wrong for
`SMNS` by a factor of ten — trading a visibly wrong default for an invisibly wrong
one. Recorded in `THEORY.md` §8.1 instead.

**Recommended fix, not implemented:** a check at calibration-finish and
config-load time that warns when a configured threshold falls outside the
[min, max] range of the loaded session's metric. That is setup-independent, needs
no tuning, and would have surfaced both this and S-5 immediately.

### S-3 — The exceedance ratio measures residual *shape*, not residual size · Major · verified numerically

Because `dynamic_threshold = ratio × max(|residual|)`, multiplying a residual by any
constant leaves the exceedance ratio unchanged. The metric is invariant under
rescaling **by construction**, so it carries no information about how large the
residual is — only about how peaked it is relative to its own maximum. The
scale-invariance was the explicit goal of the v0.11.0 rework (immunity to y-axis
miscalibration, `THEORY.md` §2.2 "Why a relative threshold"); the cost was not stated.

Reproducing the exact runtime path (`butter(7, 0.07, 'sos')` + `sosfiltfilt`,
`ratio = 0.10`, `threshold = 0.70`) on synthetic 800-px traces built from a 4-mode
FRF and quantised to integer screen rows:

| synthetic case | `exceedance_ratio` | `max|res|` px | verdict |
|---|---|---|---|
| clean trace | 0.095 | 57.2 | GOOD |
| double-hit comb ripple | 0.092 | 56.6 | GOOD |
| broadband noisy trace | 0.444 | 59.3 | GOOD |
| single spike / dropout | 0.066 | 86.5 | GOOD |
| three spikes | 0.059 | 89.1 | GOOD |
| clipped overload plateau | 0.170 | 29.5 | GOOD |

*(Reproduced exactly by the script in Appendix A.1.)*

Three mechanisms, all visible above:

- **Impulsive defects push the metric down.** One spike sets a large `max`; the rest
  of the residual falls below `0.10 × max`, so the ratio *drops* — 0.059–0.066 for
  the spike cases against 0.095 for the clean trace. The metric is **anti-correlated**
  with dropouts and clipping artefacts.
- **Comb ripple is invisible.** The double-hit case (0.091) is indistinguishable from
  clean (0.095). A near-sinusoidal residual has a near-fixed exceedance ratio
  regardless of amplitude.
- **Only broadband roughness moves it in the intended direction** (0.450).

The synthetic numbers are illustrative of the mechanism, not of field magnitudes —
the real reconstruction involves HSV masking, per-column averaging and interpolation.
But the mechanism follows from the algebra of the threshold, so it holds regardless,
and the real-data inversion in S-1 (AUC 0.368) is what it predicts.

`THEORY.md` §2.2 previously contained both the wrong explanation and, immediately
after it, a partially correct correction that still concluded a clean signal has
`exceedance_ratio ≈ 1.0` and "is not flagged because the threshold (0.7) is also
high" — which is self-contradictory, since 1.0 > 0.7 would be flagged. Real clean
signals measure 0.30–0.90. Rewritten (T-3).

### S-4 — The FFT energy ratio of a clean trace is dominated by spectral leakage · Major · verified numerically

`analyze()` removes only the **mean** before `rfft`, and applies **no window**. An
FRF trace across an ROI is not periodic and generally has a large end-to-end
discontinuity, which leaks a `1/f` skirt across the whole spectrum. On the clean
synthetic trace, with the default `fft_cutoff_frequency = 0.07`:

| preprocessing | `energy_ratio` |
|---|---|
| mean removal only *(current)* | **0.00557** |
| linear detrend | 0.00318 |
| Hann window | 0.00026 |

The default threshold is `0.006`. **A perfectly clean trace sits at 93 % of the
threshold on leakage alone**, and a Hann window removes 21× of it. The quantity the
FFT method thresholds is therefore substantially an artefact of the ROI boundary
rather than a property of the trace, which is a plausible contributor to S-1 and S-2
alike.

**Not changed.** Adding a window or a linear detrend shifts every `energy_ratio`
value and so invalidates all stored calibrations and every `fft_energy_ratio_threshold`
in `configs/`. It needs a migration and a re-labelled validation set, and
`SPEC_CLASSIFICATION_V2.md` §3.2 replaces this statistic outright with the spectral
rolloff `R_q`, roughness `ρ` and flatness `SFM` — which are self-normalising and do
not have this failure mode. Recommendation: when implementing the spec, apply a
Hann window (or at minimum a linear detrend) before `rfft`, and record in
`THEORY.md` that the legacy `energy_ratio` is not comparable across the change.

### S-5 — Confidence level never tests separability · Major · verified by execution

`confidence_level` counts labelled samples and nothing else. `no_OCR.json` stores 19
signals whose `exceedance_ratio` is **identically 0.000** — a constant, zero-variance
feature — and the engine reports **Level 4, "Robust — high confidence"**. Nothing in
the pipeline checks that a metric varies, let alone that the classes separate.

`THEORY.md` §5.6 states this openly ("No likelihood-ratio test on whether GOOD and
BAD distributions are actually distinguishable… it is the user's job to look at the
calibration plot and notice this"). `README.md` contradicted it with "Solid —
cross-validated" and "Robust — high confidence"; both labels are corrected (T-10).

A related symptom, now visible post-C-1: the merged `relative_residual_ratio` lands
on 0.02–0.025 for both sessions — the **floor of the sweep grid**. A sweep that
maximises `mean(bad) − mean(good)` on non-separating classes has no interior optimum
and saturates at a boundary. A boundary-saturated estimate is a reliable signature of
"this parameter is not identifiable from this data" and should be surfaced as a
warning rather than applied.

The `no_OCR` session makes the point sharply. Its `exceedance_ratio` is identically
zero for all 19 signals, and the engine — reporting Level 4 throughout — derives
`exceedance_ratio_threshold = 0.00000` from it. A zero-variance feature should abort
threshold estimation for that parameter, not yield a degenerate threshold that is
then written into the config and applied to live measurements.

**Recommended, not implemented:** expose per-metric AUC beside the confidence level
(the machinery exists in `ROCYoudenEstimator`), and refuse to apply — or at minimum
flag — a threshold whose metric has AUC within, say, 0.15 of 0.5, or whose estimate
saturates at a grid boundary.

### S-6 to S-9 — Method issues, open · static

- **S-6 (fixed in docs):** `_merge_all` collects three estimates, and if they disagree
  by more than 15–20 % drops the most deviant and averages the rest. That is a
  trimmed mean of three. `README.md` called it "cross-validates across all three
  methods"; there is no held-out data and no generalisation estimate anywhere in the
  engine. Terminology corrected in `README.md`; `THEORY.md` §5.5 was already accurate
  ("a poor man's robust mean").
- **S-7:** `PercentileBoundaryEstimator` fits five parameters — two filter cutoffs and
  three thresholds — from a minimum of 3 GOOD + 3 BAD, by exhaustive sweep, with no
  held-out data. That is textbook overfitting, and the sweep score
  `separation = mean(bad) − mean(good)` is an unnormalised difference of means: it
  ignores within-class variance, so it is not a separability measure and can be
  maximised where the classes merely spread wider. A rank statistic (AUC) or a
  standardised effect size (Cohen's *d*) is the appropriate score. Recorded in
  `THEORY.md` §5.2; not changed in code, because it is a method change rather than a
  defect repair and belongs with the spec work.
- **S-8:** `_find_boundary` falls back to `np.percentile(good_values, 95)` on
  overlapping classes and `THEORY.md` describes this as pinning the false-positive
  rate at 5 %. With `n_good = 3`, `np.percentile(…, 95)` is an interpolation between
  the two largest values; the realised false-positive rate is neither 5 % nor
  estimable. The rule is defensible as a heuristic, not as a rate guarantee.
- **S-9:** `get_estimates()` — the untyped path, still used by
  `get_threshold_history()` and hence by the convergence subplot — pools FRF and PSD

## 5. Performance (P) — all open, none scientific

Measured by reading the capture path; none of these affects correctness, and at the
default 0.25 s interval none is currently limiting. Listed in order of payoff.

- **P-1 — `mss.mss()` is constructed on every frame.** `_capture_screen` opens
  `with mss.mss() as sct:` per call, re-initialising the platform capture context
  4×/s. Hoist it to an instance attribute created on the worker thread (the mss
  context is not thread-portable, so construct it inside `_monitoring_loop`, not
  `__init__`).
- **P-2 — the whole monitor is captured, then cropped.** ROIs are typically a small
  fraction of the screen. `sct.grab()` accepts a bounding box; grabbing the union of
  enabled ROIs would cut both capture and transfer substantially. Combined with P-3,
  `np.array(screenshot)` followed by `cv2.cvtColor(BGRA2BGR)` allocates two
  full-screen buffers per frame — on a 4K display roughly 66 MB/frame, ~260 MB/s of
  churn at the default interval, which is what keeps the GC busy.
- **P-3 — `all_rois[name] = roi.copy()` runs for every ROI on every frame**, even when
  image logging is disabled. The slice is already a view; copy only when a logging
  path will consume it.
- **P-4 — `FRFAnalysisResult` carries `roi_image.copy()` and `color_mask.copy()`**,
  and a `frame_update` event containing them is pushed to a 100-deep queue every
  frame. The live readout needs only scalars. Send a lightweight event for
  `frame_update` and keep the images on the `hit_detected` path.
- **P-5 — `get_threshold_history()` is O(n) full refits.** It replays every signal
  through a fresh engine and calls `get_estimates()` at each step; each call runs the
  percentile sweep (46 FFT candidates + 17 LP candidates, the latter with a
  `sosfiltfilt` per signal per candidate). For 20 signals that is on the order of
  6 800 filter operations, on the Tk thread, every time Cal. Diagnostics refreshes —
  and `include_ci=True` adds a Bayesian CI replay per step. Cache by signal count.
- **P-6 — `to_dict()` calls `get_estimates_by_type()`**, i.e. two complete refits,
  on every config save.
- **P-7 — oversized functions**: `_handle_logging()` 256 lines, `_setup_main_gui()`
  226, `_process_frame()` 132. `main_window.py` is 1955 lines and carries three star
  imports (C-8), so its namespace cannot be determined by reading.

## Appendix A — Reproducing the results

### A.1 Mechanism demonstrations (synthetic)

Establishes: the `np.trapz` removal (C-1), the exceedance-ratio direction (S-3), the
Bayesian count-dependence (C-4), the `sosfiltfilt` length table (C-5), and the
leakage figures (S-4). Requires only `numpy` and `scipy`.

```python
import numpy as np
from scipy.signal import butter, sosfiltfilt

# --- C-1
print(hasattr(np, 'trapz'), hasattr(np, 'trapezoid'))   # NumPy 2.x -> False True

# --- S-3 : exceedance ratio vs contamination type
W, H = 800, 400
f = np.linspace(0, 1, W)
modes = [(0.12,.008,1.0), (0.31,.010,.7), (0.55,.012,.5), (0.80,.015,.35)]
Hc = sum(A/((fn**2 - f**2) + 2j*z*fn*f) for fn, z, A in modes)
db = 20*np.log10(np.abs(Hc) + 1e-9)
to_px = lambda d: np.round((d - (db.min()-5))/((db.max()+5)-(db.min()-5))*(H-1))

def exc(sig_px, ratio=0.10, cut=0.07, order=7):
    d = np.asarray(sig_px, float); d = d - d.mean()
    r = d - sosfiltfilt(butter(order, cut, btype='low', output='sos'), d)
    m = float(np.max(np.abs(r)))
    return float(np.sum(np.abs(r) > (ratio*m if m > 1e-9 else 0.0))/len(r)), m

rng = np.random.default_rng(0)
spike1 = to_px(db).copy(); spike1[400] += 90
spike3 = to_px(db).copy()
for i in (200, 400, 600): spike3[i] += 90
cases = [("clean",            to_px(db)),
         ("double-hit comb",  to_px(db + 3.0*np.cos(2*np.pi*18*f))),
         ("broadband noise",  to_px(db + rng.normal(0, 1.5, W))),
         ("single spike",     spike1),
         ("three spikes",     spike3),
         ("clipped plateau",  np.minimum(to_px(db), H*0.75))]
for name, s in cases:
    e, m = exc(s); print(f"{name:18s} exc={e:.3f} max={m:7.2f} -> {'BAD' if e>0.70 else 'GOOD'}")

# --- C-4 : Bayesian MAP depends only on the GOOD/BAD counts
grid = np.linspace(0.02, 0.50, 300); steep = 20.0/(0.50-0.02); c = 0.10
def MAP(ng, nb):
    p = np.ones(300)/300
    for _ in range(ng): p *= 1/(1+np.exp(np.clip(-steep*(grid-c), -500, 500))); p /= p.sum()
    for _ in range(nb): p *= 1/(1+np.exp(np.clip(-steep*(c-grid), -500, 500))); p /= p.sum()
    return grid[np.argmax(p)]
for ng, nb in [(3,3),(6,3),(3,6),(8,8)]: print(ng, nb, round(MAP(ng,nb), 4))

# --- C-5 : sosfiltfilt minimum length
for order in (3,5,7,10):
    sos = butter(order, 0.07, btype='low', output='sos')
    print(f"order {order:2d}: needs len > {3*(2*len(sos)+1)-1}")

# --- S-4 : leakage
from scipy.fft import rfft, rfftfreq
def er(sig, cut=0.07):
    d = sig - sig.mean(); m = np.abs(rfft(d)); xf = rfftfreq(len(d), 1)
    i = np.where(xf >= cut)[0]
    return float(np.sum(m[i[0]:]**2)/np.sum(m**2))
clean = np.asarray(to_px(db), float)
lin = np.polyval(np.polyfit(np.arange(W), clean, 1), np.arange(W))
print("mean-detrend", round(er(clean),5), "| linear", round(er(clean-lin),5),
      "| Hann", round(er(clean*np.hanning(W)),5), "| threshold 0.006")
```
